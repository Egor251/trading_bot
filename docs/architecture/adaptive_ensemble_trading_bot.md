# Технический документ: Алгоритмический торговый бот с адаптивным консилиумом стратегий

**Версия:** 1.0  
**Дата:** 25 июля 2026 г.  
**Статус:** Проектная документация  
**Репозиторий:** `trading_bot`

---

## 1. Введение

### 1.1. Назначение системы
Разработка алгоритмического торгового бота, основанного на архитектуре **«консилиума стратегий»** с динамическим распределением капитала, адаптивной подстройкой параметров и фантомным контуром валидации в реальном времени.

### 1.2. Ключевые цели
- Создание отказоустойчивой торговой системы, не зависящей от работоспособности одной стратегии.
- Автоматическая адаптация к смене рыночных режимов (тренд / флэт / высокая волатильность).
- Защита от переобучения через фантомный прогон и поиск робастных «плато параметров».
- Разделение торгового ядра и UI для обеспечения бесперебойной работы.

### 1.3. Целевые рынки
- Криптовалютный рынок (через CCXT).
- Фондовый рынок (через Alpaca / Interactive Brokers API).
- Фокус на средне- и низкочастотных стратегиях (не HFT).

**Universe (обязательный слой):** из тысяч инструментов live идёт только **active book**.  
Каталог не стримится целиком. Отбор **настраиваемый и адаптивный**: `manual` или screener-профили  
(`liquid` / `volatility` / `futures_speculation` / options…), не один зашитый критерий.  
Канон: [`universe_selection.md`](universe_selection.md), [`philosophy.md`](philosophy.md).

### 1.4. Философия и эталон

Ключевые идеи уже заложены в **Code_base** и обкатаны в **easm-gate-guardian**:

| Принцип | Смысл |
|---------|--------|
| Микроядро | Тонкий Engine: EventBus, plugins, services, rules |
| Модульность | Стратегии / брокеры / риск / фантом / мета / UI / **universe** — сменные модули |
| **Максимальная настраиваемость** | YAML + plugin settings + rules + **universe profiles**; ничего критичного не зашито |
| **Максимальная адаптивность** | Regime / веса консилиума / параметры **и** смена критерия отбора бумаг под стратегию и режим |

Эти два последних принципа **сквозные**: они относятся и к консилиуму, и к **отбору инструментов под торговлю**  
(не один «ликвидный» screener на весь продукт).

**Эталон формы продукта:** GateGuardian (хост + plugins + services + отдельный UI-контур).  
**Домен:** алготрейд / консилиум (не NDR).

Подробно: [`philosophy.md`](philosophy.md), [`universe_selection.md`](universe_selection.md).

### 1.5. Связь с текущим кодом
Существующий хост на `microkernel_core` (`host/`, `services/`, `plugins/`) — база Engine.  
Legacy v1 удалён из `main` (тег `legacy-v1`).  
Целевой UI — отдельный процесс Dear PyGui + ZeroMQ (не блокирует Engine).

### 2.2. Принципы разделения процессов

| Процесс | Назначение | Критичность |
|---------|------------|-------------|
| **Engine** | Торговая логика, исполнение | Критичен (не должен падать) |
| **UI** | Визуализация, управление | Некритичен (может перезапускаться) |
| **Data Collector** | Сбор и хранение данных | Высокая критичность |
| **Phantom Worker** | Фантомные прогоны | Средняя (может работать асинхронно) |

**Правило:** UI никогда не блокирует Engine. При падении UI торговля продолжается.

## 3. Компоненты системы

### 3.1. Торговое ядро (Engine)

**Ответственность:**
- Подключение к биржам и получение рыночных данных.
- Управление жизненным циклом ордеров.
- Исполнение стратегий консилиума.
- Контроль рисков на уровне портфеля.

**Ключевые модули:**
- `UniverseManager` / `universe_service` — отбор инструментов (catalog → candidates → active); market adapters стримят только active.
- `MarketDataAdapter` — унифицированный интерфейс к биржам (через CCXT) **по active book**.
- `OrderManager` — управление ордерами с учётом частичного исполнения.
- `RiskManager` — контроль позиции, стоп-лоссы, лимиты просадки.
- `EnsembleManager` — координация стратегий консилиума.

### 3.1.1. Universe Selection

**Проблема:** тысячи инструментов; live по всем не тянет. Критерий отбора **зависит от стратегии**.

**Решение:** воронка catalog → **screen profile** → active; не один глобальный «top по объёму».

| Профиль | Ранг | Типичный use-case |
|---------|------|-------------------|
| `liquid` | dollar_volume | классический QC/Zipline |
| `volatility` | atr_pct / realized_vol | vol play (+ пол ликвидности) |
| `futures_speculation` | volume в futures | спекуляция с низкими комиссиями vs акции |
| `options_underlying` | iv_rank | базисы для опционов; chain — отдельно |

Консилиум: per-strategy books → **union** в глобальный active.  
Опционы: underlying screen сейчас; chain (DTE/delta/OI) — отдельный этап.  
Канон: [`universe_selection.md`](universe_selection.md).

### 3.2. Консилиум стратегий

**Требования к стратегиям:**
- Стратегии должны быть **ортогональными** (корреляция доходностей < 0.6).
- Минимум 3-5 стратегий разной природы:
  1. Трендовая (пробой уровней, momentum).
  2. Возврат к среднему (mean reversion).
  3. Волатильностная (торговля на новостях, VIX-подобные).
  4. Микроструктурная (анализ стакана, order book imbalance).
  5. На альтернативных данных (NLP новостей, ончейн).

**Механизм работы:**
- Каждая стратегия имеет свой вес в портфеле.
- Веса пересчитываются динамически (см. раздел 4.3).

### 3.3. Фантомный контур (Shadow Trading)

**Назначение:**
- Параллельный прогон вариаций параметров основной стратегии.
- Валидация гипотез без риска реальным капиталом.
- Поиск робастных «плато параметров».

**Требования к реалистичности:**
- Учёт комиссий (maker/taker).
- Учёт проскальзывания (модель slippage на основе объёма).
- Учёт задержек (latency) получения данных.
- Моделирование частичного исполнения ордеров (partial fills).

### 3.4. Мета-модуль (AI / ML)

**Задачи:**
1. **Классификация режимов рынка** (Regime Detection).
2. **Multi-Armed Bandit** для выбора стратегии.
3. **Parameterized Meta-Model** для предсказания оптимальных параметров.
4. **NLP-анализ** новостей и тональности.

### 3.5. UI (Dear PyGui)

**Функционал:**
- Отображение equity curves фантомных стратегий в реальном времени.
- Таблицы текущих параметров консилиума.
- Тепловые карты поиска плато параметров.
- Матрица корреляций стратегий.
- Логи исполнения и статусов.
- Кнопки управления (START / STOP / Emergency Kill Switch).

## 4. Алгоритмы и механики

### 4.1. Динамическое распределение стратегий

**Метод:** Multi-Armed Bandit (Upper Confidence Bound / Thompson Sampling).

**Принцип:**
- Баланс между *эксплуатацией* (капитал в лучшие стратегии) и *исследованием* (проверка остальных).
- Избегание ситуации, когда лучшая стратегия внезапно сломалась, а система этого не замечает.

**Формула UCB:**
```
A_t = argmax_a [ Q_t(a) + c * sqrt(ln(t) / N_t(a)) ]
```
где `Q_t(a)` — средняя доходность стратегии `a`, `N_t(a)` — количество её «использований», `c` — коэффициент исследования.

### 4.2. Адаптивная подстройка параметров

**Вместо смены стратегии — подстройка её параметров.**

**Правила:**
1. **Поиск плато, а не пика.** Grid Search + кластерный анализ или Байесовская оптимизация с оценкой дисперсии.
2. **Условная оптимизация.** Параметры подбираются в привязке к режиму рынка.
3. **Гистерезис.** Новый параметр принимается только если преимущество статистически значимо и перекрывает стоимость ребалансировки.
4. **Walk-Forward валидация.** Параметр из окна A проверяется на окне B до допуска в бой.

**Запрещено:**
- Градиентный спуск для поиска параметров.
- Менять параметры чаще заданного интервала (например, раз в неделю).

### 4.3. Распределение капитала (Risk Parity)

```
w_i = (1 / σ_i) / Σ(1 / σ_j)
```
где `σ_i` — волатильность доходности i-й стратегии.

### 4.4. Мета-маркирование (Meta-Labeling)

Вторая модель (Random Forest / XGBoost) предсказывает, *сработает ли сигнал* основной стратегии.

**Входные признаки:** ATR/волатильность, объём, ADX, время суток, макро, тональность новостей.  
**Выход:** вероятность успеха; ниже порога — сигнал игнорируется.

### 4.5. Классификация режимов рынка

**Методы:** HMM, K-Means, пороговые правила (ATR).

**Режимы:**
1. Сильный тренд
2. Слабый тренд / флэт
3. Высокая волатильность
4. Низкая волатильность
5. Шоковый режим

## 6. Потоки данных

### 6.1. Основной торговый цикл

```
0. universe_service: catalog → screen → active; publish universe.changed
1. Market Data Adapter стримит только active (тик/свеча)
2. Данные → внутренняя шина (EventBus / Redis / ZMQ)
3. Стратегии консилиума получают данные
4. Мета-модуль определяет режим рынка
5. Meta-Labeling фильтрует сигналы
6. EnsembleManager агрегирует с весами
7. Risk Manager проверяет лимиты
8. Order Manager исполняет на бирже
9. Результаты → UI и хранилище
```

### 6.2. Фантомный контур

```
1. Phantom Worker получает те же данные
2. N вариаций параметров
3. Распределение результатов → отсев ниже 80% пика
4. Кластер «хороших» параметров (плато) → медиана
5. Walk-Forward → при успехе публикация в Engine
6. Engine применяет с гистерезисом
```

### 6.3. Связь UI ↔ Engine

| Канал | Направление | Содержимое |
|-------|-------------|------------|
| 5555 | Engine → UI | equity, параметры, статусы (1–10 Гц) |
| 5556 | UI → Engine | START / STOP / KILL |

## 7. Риск-менеджмент

### 7.1. Уровни защиты

| Уровень | Механизм | Действие |
|---------|----------|----------|
| Сделка | SL / TP | Закрытие позиции |
| Стратегия | max DD −5% | Приостановка стратегии |
| Консилиум | Корреляционный фильтр | Снижение веса |
| Портфель | max DD −10% | Полная остановка |
| Система | Kill Switch | Аварийное закрытие всех |

### 7.2. Аварийные сценарии
- Падение UI → Engine продолжает
- Падение Engine → закрытие позиций по рынку
- Потеря связи с биржей → только закрытие
- Flash crash → пауза до ручного подтверждения

### 7.3. Лимиты по умолчанию
- Max DD консилиума: −10%
- Max DD стратегии: −5%
- Max позиция в активе: 20% депозита
- Плечо: 1x на старте

## 8. Валидация и тестирование

- Walk-Forward Optimization (обязательна)
- Purged K-Fold
- Комиссии, slippage, market impact
- Фантом 2–3 месяца; расхождение с live < 15%
- Переключение при p < 0.05; ≥100 сделок для оценки

## 10. Критерии успеха

- UI не блокирует Engine
- Фантом vs live < 15%
- 24/7 без ручного вмешательства > 30 дней

### Финансовые
- Sharpe консилиума > 1.5 / 6 месяцев
- Max DD < 10%
- Попарная corr стратегий < 0.6

- Recovery < 5 минут
- Автоостановка на авариях

## 12. Заключение

Отказ от поиска единственной «граальной» стратегии в пользу управления портфелем стратегий с постоянной валидацией через фантомный контур. Архитектурное разделение UI и Engine через ZeroMQ гарантирует, что визуализация не станет причиной торговых потерь.
